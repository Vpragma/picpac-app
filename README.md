# PicPac App — прототип для хакатона (трек 2)

Мобильное веб-приложение PicPac в стиле super.picpac.by: каталог, карточка продукта, выбор фото, автомакет, проверка перед заказом, корзина, заказ со статусами.

Настоящие аккаунты: вход и регистрация на сервере, база клиентов в Supabase, роли «клиент», «модератор» и «администратор» с проверкой прав на сервере (ОТ-02), журнал действий (ОТ-04).

## Тестовые аккаунты

| Почта | Роли | Что увидите |
|---|---|---|
| client@example.com | клиент | профиль и заказы; админка закрыта (403) |
| moderator@example.com | модератор | админка: заказы; журнал действий закрыт (403) |
| admin@example.com | клиент + администратор | экран выбора роли; в роли администратора — журнал действий |

Пароль для всех трёх: `PicPac-kchQ-XBUz-4tqK`

Это синтетические аккаунты, реальных людей нет. Удалить их из профиля нельзя — ими пользуются все проверяющие. Чтобы проверить удаление аккаунта, зарегистрируйте свой. Вернуть тестовым аккаунтам пароль и роли: `npm run seed`.

## Как проверить за 3 шага

1. Откройте приложение без входа: каталог, редактор и корзина работают. В корзине «Подтвердить заказ» попросит войти и вернёт обратно — корзина и черновик на месте.
2. Войдите как `client@example.com` и откройте `/admin` — «Нет доступа» (код 403). Попытка попадёт в журнал.
3. Выйдите, войдите как `admin@example.com`, выберите «Администратор» → «Админка» → «Журнал действий».

## Запуск у себя

```bash
npm install
vercel env pull .env.local
npm run db:migrate
npm run seed
npm run seed:catalog
npm run dev
```

- `vercel env pull .env.local` — скачивает ключи Supabase из проекта Vercel в `.env.local` (в git этот файл не попадает).
- `npm run db:migrate` — создаёт таблицы и правила доступа в базе. Повторный запуск безопасен.
- `npm run seed` — создаёт тестовые аккаунты. Нужен `SEED_PASSWORD` в `.env.local` — пароль из таблицы выше. Повторный запуск безопасен.
- `npm run seed:catalog` — наполняет каталог в базе: 5 продуктов, размеры, опции, 5 способов доставки, тестовые промокоды. Повторный запуск обновляет строки, дублей нет.

## Вход и роли (ОТ-02)

- Всё проверяет сервер. Пароль проверяет Supabase Auth. Сессия хранится в cookies с флагом httpOnly — JavaScript страницы их не видит; на Vercel cookies передаются только по HTTPS.
- Роли лежат в таблице `user_roles`. Новый пользователь автоматически получает роль «клиент».
- Экран выбора роли показывается только после входа и только если ролей больше одной. Клиент с одной ролью сразу попадает в приложение.
- Выбранная роль хранится в httpOnly-cookie `pp_role`, но сама прав не даёт: сервер в каждом запросе сверяет её с базой. Подменённая cookie даёт отказ 403, и попытка пишется в журнал.
- Роль сотрудника действует 12 часов, потом её нужно выбрать снова.
- Три линии защиты:
  1. `proxy.js` — проверяет вход и роль до того, как откроется страница или API;
  2. сама страница или обработчик API проверяет ещё раз (`lib/server/session.js`);
  3. правила RLS в базе: пользователь видит только свой профиль и свои роли, админ — всё через функцию `has_role()`; писать роли может только сервер.
- Без входа — код 401 и страница «Нужно войти», без нужной роли — 403 и страница «Нет доступа».
- Ограничение попыток входа: после 10 неудачных попыток на одну почту или 30 с одного IP за 15 минут вход закрывается на 15 минут.
- Защита от подделки запросов с чужих сайтов: API принимает только JSON и проверяет заголовок Origin.
- Ошибки по-русски и без подсказок взломщику: на любую ошибку входа — «Неверная почта или пароль».

| Раздел | Гость | Клиент | Модератор | Админ |
|---|---|---|---|---|
| Каталог, редактор, корзина | да | да | да | да |
| Подтвердить заказ | после входа | да | да | да |
| Профиль | гостевой режим | да | да | да |
| `/admin` — заказы | 401 | 403 | да | да |
| `/admin/audit`, `/api/v1/admin/audit` — журнал | 401 | 403 | 403 | да |

## Двухфакторный вход для сотрудников

Модератор и администратор могут входить с кодом из приложения-аутентификатора (Google Authenticator, Яндекс Ключ, 1Password и другие). Это Supabase MFA, коды TOTP.

Включается флагом `REQUIRE_STAFF_MFA` в настройках Vercel или в `.env.local`:

- `REQUIRE_STAFF_MFA=true` — для ролей «модератор» и «администратор» код обязателен. При первом входе с такой ролью приложение показывает QR-код: его нужно отсканировать в приложении-аутентификаторе и ввести 6 цифр. Дальше при каждом входе с ролью сотрудника — только код. Сервер проверяет код в каждом запросе к админке (уровень сессии `aal2`), и в `proxy.js`, и в обработчике.
- Флаг не задан или `false` — код не спрашивается. **Так настроен демо-стенд**: иначе жюри не сможет войти в общие тестовые аккаунты, ведь код приходит только на один телефон. Подключённое раньше приложение-аутентификатор при выключенном флаге вход не блокирует.

Как проверить у себя: добавьте `REQUIRE_STAFF_MFA=true` в `.env.local`, запустите `npm run dev`, войдите как `admin@example.com` и выберите «Администратор». Автотест: `npm run test:mfa` (см. раздел «Запуск у себя»).

Убрать подключённый код у аккаунта: Supabase → Authentication → Users → пользователь → MFA factors → удалить.

## Журнал действий (ОТ-04)

- Таблица `audit_log`: когда (`at`), кто (`user_id`, `role`), что (`action`), над чем (`object_type`, `object_id`), чем закончилось (`result`: success / denied / error), подробности (`details`) и IP.
- Записываются: вход (успех и ошибка), регистрация, выбор роли, выход, отказ в доступе, изменение профиля, удаление аккаунта, подключение и проверка кода 2FA; проекты (`project.create/update/delete`), фото (`photo.upload_url/add/reorder/delete/view`), корзина (`cart.update/merge`), промокоды (`promo.validate`), заказы (`order.create/view/pay_test`), обращения (`interaction.create/message/view`), выгрузка и удаление данных (`account.export/delete_photos`). Попытки открыть чужой объект пишутся с результатом `denied`.
- Записи нельзя изменить или удалить никому, даже серверу с секретным ключом: это запрещают права и триггер в базе. Записи остаются и после удаления аккаунта.
- Экран `/admin/audit` (только администратор): последние 100 записей, время по Минску (UTC+3).

## База данных

Миграции лежат в `supabase/migrations/` и применяются командой `npm run db:migrate`. Применённые файлы записываются в служебную таблицу `private.schema_migrations`, поэтому повторный запуск ничего не ломает.

| Таблица | Что хранит |
|---|---|
| `profiles` | имя пользователя и дата создания; `id` совпадает с id в Supabase Auth |
| `user_roles` | роли пользователей; пара «пользователь — роль» уникальна |
| `audit_log` | журнал действий, только добавление |
| `products`, `product_sizes`, `product_options` | каталог: продукты, размеры (коэффициент цены), опции (обложка, ламинация, бумага, печать, поверхность) |
| `delivery_methods`, `promo_codes` | способы доставки и тестовые промокоды |
| `addresses` | сохранённые адреса получателя |
| `projects`, `project_photos` | проекты клиента (опции, статус, `version` — защита от затирания) и их фото в хранилище |
| `cart_items` | корзина на сервере |
| `orders`, `order_items`, `order_status_history` | заказы (номер `PP-ГГММДД-NNNNN`, суммы в копейках, ключ идемпотентности), состав-снимок, лента статусов |
| `interactions`, `interaction_messages` | обращения по заказу и переписка (клиент, бот, оператор) |
| `notifications`, `notification_settings`, `push_subscriptions` | уведомления и подписки на пуши |
| `analytics_events`, `moderation_reviews`, `data_requests` | обезличенная аналитика, модерация фото, запросы на удаление данных |

Правила доступа (RLS) включены на всех таблицах: гость не видит ничего, клиент — только своё, модератор — очередь модерации, админ — всё; писать может только сервер после своих проверок. Фото лежат в приватном бакете `photos` (только JPEG/PNG до 25 МБ), путь `{user_id}/{project_id}/{uuid}.jpg`; загрузка и просмотр — только по подписанным ссылкам сервера (просмотр — 10 минут). Лимиты частоты — функция `rate_limit_hit` и таблица `private.rate_limits`.

Ещё в базе: тип `app_role` (client, moderator, admin), функция `has_role()` для правил доступа, триггер `on_auth_user_created` — новому пользователю создаёт профиль и даёт роль «клиент».

## Каталог и цены

- Каталог хранится в базе и приходит в приложение только через `GET /api/v1/catalog`: 5 продуктов (Lite, Classic, Premium, Печать фото, Цифровая печать), размеры, опции, цены, сроки, требования к фото, 5 способов доставки. Источник данных — `docs/superpicpac/superpicpac.md`.
- Требования к фото: JPEG или PNG до 25 МБ; на своём месте в печати ≥ 300 точек на дюйм — отлично, ≥ 150 — хорошо, 100–150 — предупреждение «может быть нечётко», < 100 — «будет размыто».
- Тестовые промокоды: `TEST10` (−10%), `FREESHIP` (бесплатная доставка), `PICPAC5` (−5,00 руб. от 50,00), `OLD2025` (истёкший — для проверки сообщения «Истёк»).

### Формулы (ОТ-07)

Деньги в базе — целые копейки и валюта `BYN`; даты — `timestamptz` (UTC), показываем по Минску (`Europe/Minsk`, UTC+3). Формулы одни и те же в интерфейсе и на сервере — `lib/pricing.js`, проверяются `npm run test:unit`.

| Что | Формула |
|---|---|
| Коэффициент размера книги | `k = 1 + 0,6 × (ширина × высота ÷ 400 − 1)`; 20×20 → 1, 21×30 → 1,345, 30×30 → 1,75. **Коэффициенты размеров тестовые — уточнить у Фотопринт** |
| Цена книги | `(база + надбавка_за_2_стр × (страниц − мин) ÷ 2) × k`, округление до 0,10. Проверка (20×20): Classic 60 стр. = 141,00; Lite 160 = 206,00; Premium 60 = 275,50 |
| Цена печати фото | `цена_отпечатка_размера × число_фото` |
| Надбавка опций | к цене книги (или отпечатка) прибавляется `price_delta_kop` выбранных опций; сейчас у всех опций 0 — на сайте опции цену не меняют |
| Строка заказа | `цена_за_единицу × количество` |
| Скидка промокода | `percent`: товары × % ÷ 100 (округление до копейки); `amount`: min(сумма кода, товары); `free_delivery`: 0. Код действует, только если товары ≥ мин. суммы и сейчас внутри срока действия |
| Доставка | 0, если промокод `FREESHIP` или (товары − скидка) ≥ «бесплатно от» способа; иначе цена способа |
| Итого | товары − скидка + доставка |
| Срок | сегодня по Минску + срок печати (книги 3 дня, фото 2) + дни доставки способа (от–до) |
| Номер заказа | `PP-ГГММДД-NNNNN`: дата по Минску + порядковый номер из последовательности базы (без случайных цифр и совпадений) |

## Каталог, карточка и редактор на устройстве (S02a–b)

- **Каталог без лишних запросов.** Главная и карточка продукта отрисовываются на сервере из той же базы, что `GET /api/v1/catalog` (главная обновляется раз в минуту, ISR). Браузер на этих страницах каталог не запрашивает; на остальных экранах — один общий запрос (`lib/useCatalog.js`).
- **Карточка продукта:** размер (у каждого — своя цена), обложка, ламинация страниц (по умолчанию как обложка), бумага, тип печати, поверхность, страницы, количество. Цена считается сразу по `lib/pricing.js` — той же формуле, что на сервере. Срок — по Минску: «Напечатаем за 3 дня — доставим ориентировочно 17–18 ноября» (печать + дни первого способа доставки), сроки и цены остальных способов — под спойлером. Блок «Требования к фото» с точными пикселями для выбранного размера.
- **Мои книги и фото:** несколько проектов на устройстве (IndexedDB) со статусами «Черновик», «В корзине», «Заказан». «Создать» для другого продукта открывает новый проект и не трогает прежние. Раздел «Заказанные»: «Открыть заказ» и «Заказать ещё раз» (копия проекта с теми же фото — заказанный проект не меняется).
- **Редактор:** шаги «Фото · Автомакет · Правки · Проверка · Заказ · Статус». Фото с устройства (JPEG/PNG, сразу несколько; на компьютере — перетаскиванием файлов в окно) или кнопкой «Тестовая галерея» (выбор фото из `public/demo-gallery`). По каждому фото видно «ждёт очереди / готовим… / не получилось» и кнопка «Повторить». Порядок: на телефоне — кнопки «раньше / позже», на компьютере — перетаскивание за значок ⠿ мышью или клавиатурой (Tab, пробел, стрелки, пробел; подсказки для экранного диктора на русском). «Правки»: кадрирование — «Заполнить место» или «Целиком» и что важнее оставить в кадре.
- **Проверка перед заказом:** пустые страницы, не поместившиеся фото, недостаточная резкость в печати (точек на дюйм на своём месте), неподдерживаемый формат (HEIC, WebP, GIF), файл больше 25 МБ. Каждое предупреждение объясняет проблему и что делать; кнопки «Заменить фото» и «Продолжить всё равно» (решение сохраняется в проекте, у вошедшего клиента — ещё и в журнале действий).
- Черновик сохраняется на устройстве сразу и переживает перезагрузку и закрытие браузера.

## Синхронизация, корзина и оформление (S02c)

- **Гость** работает только на устройстве: проекты и фото — в IndexedDB, корзина — в `localStorage`. Чтобы подтвердить заказ, нужно войти или зарегистрироваться; после входа приложение возвращает в корзину, а проекты и корзина гостя переносятся в аккаунт.
- **Вошедший клиент:** каждый проект синхронизируется с аккаунтом (`lib/sync.js`) через 1,2 с после изменения: `POST /api/v1/projects` → для каждого фото `upload-url` → `PUT` файла в хранилище → `POST photos` (сервер сам проверяет тип и размеры по байтам) → `PATCH photos/order` → `PATCH /projects/{id}` с `version`. Если проект изменили на другом устройстве (409), приложение перечитывает версию и сохраняет свои правки поверх. Без сети изменения ждут и уходят сами, когда связь вернётся. `serverId` и `version` хранятся в проекте на устройстве. Проекты аккаунта, которых нет на устройстве (вход с нового устройства), загружаются вместе с фото и порядком.
- **Корзина вошедшего** — на сервере (`/api/v1/cart`), её видно с другого устройства. Позиция, добавленная на устройстве, сначала ждёт загрузки фото («Переносим в аккаунт: загружено фото 5 из 12»), затем попадает в серверную корзину. Счётчик позиций — в шапке, с анимацией при добавлении.
- **Оформление:** получатель (имя, телефон `+375 (XX) XXX-XX-XX` с проверкой, почта), способ получения из каталога (5 способов) с зависимыми полями: пункт выдачи Европочты из тестового списка, отделение Белпочты по индексу, курьер — адрес и дата. «Сохранить адрес» — адрес появится кнопкой при следующем заказе (на устройстве). Промокод — видимое поле, «Применить» и «Убрать», сообщения «Промокод применён», «Не подходит: …», «Истёк: …» приходят с сервера. Расчёт «Товары → Скидка → Доставка → Итого» в BYN по `lib/pricing.js` сразу при любом изменении; итог заказа сервер считает заново. Оплата только тестовая: «Карта (тест)» или «ЕРИП (тест)», деньги не списываются.
- **Без дублей:** ключ `Idempotency-Key` создаётся на попытку оформления и хранится в IndexedDB до успеха. Двойное нажатие, повтор после обрыва связи или перезагрузки отправляют тот же ключ — сервер вернёт тот же заказ. Кнопка блокируется на время запроса, при ошибке сети — понятное сообщение и «Повторить», введённые данные не теряются.
- После успеха — номер заказа с сервера (`PP-ГГММДД-NNNNN`), ориентировочная дата доставки, проект переходит в «Заказанные».

## Заказы, поддержка, выход (S02d–e)

- **«Мои заказы»** — история из `GET /api/v1/orders`: номер, статус, позиции, сумма, дата; список обновляется раз в 15 секунд. Из списка открывается **экран заказа** (`GET /api/v1/orders/{id}`): состав (продукт, опции словами, число фото, миниатюры по подписанным ссылкам на 10 минут), «Товары → Скидка → Доставка → Итого» в BYN, тестовая оплата, получатель, способ и адрес доставки, ориентировочная дата.
- **Статусы — ровно 5 из ТЗ:** «Принят» → «Модерация» → «Производство» → «Готов / передан в доставку» → «Завершён». Лента показывает время каждого шага по Минску и причину смены. Пока нет мока ERP (этап S06), демо-заказы двигает сервер при чтении: через 30 секунд после тестовой оплаты — «Модерация»; ещё через 30 секунд — «Производство» автоодобрением, если ни у одного фото нет флага модерации (с флагом заказ ждёт модератора, автоматика сама не отклоняет); дальше шаг каждые 30 секунд. Смена статуса — условным обновлением в базе, поэтому одновременные чтения не задваивают ленту (`lib/server/orderFlow.js`).
- **«Написать в поддержку»** на экране заказа: тема и сообщение → обращение привязано к заказу, бот сразу отвечает, к какому сроку ответит оператор (24 часа). Обращения и переписка видны в заказе и в админке → «Заказы» (последние заказы и обращения из базы, без ФИО и адресов). Чат оператора и смена статуса с причиной — этап S06.
- **Выход (M-01):** кнопка «Выйти» сначала отправляет в аккаунт всё, что ещё не ушло (`syncAll()`). Если не получилось (нет связи) — предупреждение «Не все изменения сохранились в аккаунте» с выбором «Повторить» или «Выйти без них». Затем с устройства стираются черновики и фото (IndexedDB «picpac»: проекты, фото, ключ заказа, очередь удалений), гостевая корзина, форма оформления и адреса (`localStorage` `picpac:*`), кэш «кто вошёл», пуш-подписка — и только потом сервер закрывает сессию (`lib/device.js`). При удалении аккаунта устройство тоже очищается. После входа проекты (с фото и порядком), корзина и заказы загружаются из аккаунта.
- **Черновик на устройстве** записывается в IndexedDB не позже чем через 0,15 с после изменения (и сразу при уходе со страницы), даже при быстром добавлении многих фото подряд.
- **Экран входа** — без паролей: «Данные для входа жюри — в README проекта», кнопка «Продолжить как гость». **Профиль гостя:** «Профиль», объяснение, «Войти», «Зарегистрироваться», «Назад к каталогу».
