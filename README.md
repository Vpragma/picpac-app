# PicPac App — мобильное приложение PicPac (хакатон, трек 2)

PWA для заказа фотокниг и печати фото в стиле super.picpac.by плюс раздел для сотрудников. Один адрес, один код: клиент работает с телефона, модератор и администратор — с компьютера. Все данные тестовые и синтетические.

## Задача и ценность

**Задача (ТЗ, трек 2):** мобильный канал PicPac, который сокращает путь от фото на телефоне до оформленного заказа: каталог → проект → фото → проверка → корзина → тестовая оплата → номер заказа → статусы и поддержка, плюс админка с журналом действий.

**Ценность:**

- **Клиенту** — заказ с телефона без сайта и магазина приложений: черновик сохраняется сам (переживает перезагрузку и обрыв связи), проблемные фото видны **до** печати («Будет размыто», «Темно», «Пересвет»), простые правки словами («сделай теплее», «убери солнце»), двойное нажатие не создаёт второй заказ.
- **Фотопринт** — меньше перепечаток «ошибка в макете» (проверка качества до заказа), заказы и обращения в одном месте, обезличенная статистика воронки (где клиенты бросают проект, доля оплативших из корзины). Эффект — гипотезы с формулами, их проверяет пилот ([presentation-notes.md](docs/presentation-notes.md), раздел «Метрики эффекта»).

## Обязательный сценарий за 5 минут

1. **Каталог (гость).** Откройте демо на телефоне (или окно 390×844). Каталог → «Classic» → смените размер: цена и срок доставки по Минску пересчитываются сразу.
2. **Проект.** «Создать фотокнигу» → «Тестовая галерея» → «Добавить 12 фото» (у фото подписаны проблемы: «тёмное», «пересвет», «маленькое»…). Перезагрузите страницу — фото и порядок на месте. «Автомакет» раскладывает фото по страницам.
3. **ИИ-правки.** Шаг «Правки»: у тёмного фото значки «Темно» и «Улучшено», ползунок «До / после». В поле «Что изменить?» напишите «сделай теплее» → «Сделать». На фото «Закат» — «убери солнце». На фото «Собака с мячом»: «Выделить касанием» → коснитесь собаки → «Размыть фон»; «Сбросить» → коснитесь мяча → «Убрать».
4. **Проверка.** Шаг «Проверка»: добавьте маленькое фото (`nesvizh-small` в галерее) — предупреждение объясняет, что будет нечётко, и даёт «Заменить фото» или «Продолжить всё равно». Затем «В корзину».
5. **Заказ.** Корзина → «Подтвердить заказ» → вход `client@example.com` → снова корзина (проект перенесён в аккаунт). Имя, телефон `+375 (29) 123-45-67`, промокод `TEST10` → «Применить», «Европочта» и пункт выдачи, «ЕРИП (тест)» → «Подтвердить заказ» → номер `PP-ГГММДД-NNNNN`.
6. **Ошибка сети.** Чтобы проверить повтор без дубля: перед «Подтвердить заказ» выключите сеть (DevTools → Network → Offline) — форма цела, понятная ошибка; включите сеть и нажмите «Повторить» (можно дважды) — заказ один.
7. **Статусы и поддержка.** «Открыть заказ»: лента из 5 статусов (демо-заказ сам двигается примерно каждые 30 секунд), «Написать в поддержку» → ответ бота.
8. **Две роли и журнал.** На `/admin` под клиентом — «Нет доступа». Выйдите, войдите `admin@example.com` → «Администратор» → «Админка»: «Заказы», «Статистика» (воронка, формулы в «?»), «Журнал действий» (видна запись об отказе клиенту).

Подробный сценарий демонстрации на 5–7 минут — [docs/demo-script.md](docs/demo-script.md).

## Архитектура кратко

Браузер хранит черновики у себя (IndexedDB) и синхронизирует их с аккаунтом; сервер на Next.js (Vercel) проверяет вход и роль, считает цены и итог, пишет журнал; Supabase даёт Postgres с правилами доступа RLS, вход и закрытое хранилище фото; фото загружаются в хранилище напрямую по подписанной ссылке. ИИ-правки работают на устройстве. Схемы компонентов, потоков данных (загрузка фото, заказ с идемпотентностью, статусы, ИИ-правка), модель данных и роли — [docs/architecture.md](docs/architecture.md). API — [docs/api/openapi.yaml](docs/api/openapi.yaml) (OpenAPI 3.1) и [docs/api/examples.http](docs/api/examples.http).

## Стек

Next.js 16 (App Router, `proxy.js`) и React 19 на JavaScript; Supabase (Postgres + RLS, Auth, Storage) через `@supabase/supabase-js` и `@supabase/ssr`; `zod` — проверка ввода; `@dnd-kit` — порядок фото мышью и клавиатурой; свой Service Worker `public/sw.js` — PWA и офлайн; `postgres` — миграции; Playwright и `node:test` — тесты. ## Запуск локально (≈ 15 минут)

Нужны Node.js 20+ (проверено на 26), git и бесплатный аккаунт Supabase.

1. **Код и пакеты** (≈ 3–5 минут): `git clone https://github.com/Vpragma/picpac-app.git && cd picpac-app && npm install` (репозиторий закрытый — нужен доступ на GitHub).
2. **Свой проект Supabase** (≈ 3 минуты): supabase.com → New project (регион любой, пароль базы сохраните). Из Settings → API возьмите Project URL, publishable (или anon) и secret (или service_role) ключи; из Settings → Database → Connection string → Direct — строку подключения.
3. **Переменные** (≈ 2 минуты): `cp .env.example .env.local` и впишите значения — список ниже. Свой пароль демо-аккаунтов (`SEED_PASSWORD`) и соль аналитики (`ANALYTICS_SALT`, любая длинная строка) придумайте сами. Участники команды могут вместо этого взять значения из Vercel: `vercel env pull .env.local`.
4. **База и данные** (≈ 2–3 минуты):
   ```bash
   npm run db:migrate     # таблицы, правила RLS, функции, бакет photos (повторный запуск безопасен)
   npm run seed           # демо-аккаунты client/moderator/admin@example.com с паролем из SEED_PASSWORD
   npm run seed:catalog   # каталог: 5 продуктов, размеры, опции, 5 способов доставки, промокоды
   npm run seed:demo      # синтетические клиенты, заказы, обращения, события + демо-проекты клиента (≈ 1 минута)
   ```
5. **Запуск:** `npm run dev` → http://localhost:3000. Проверка «как на сервере»: `npm run build && npm start`.

## Вход и роли (ОТ-02)

- Всё проверяет сервер. Пароль проверяет Supabase Auth. Сессия хранится в cookies с флагом httpOnly — JavaScript страницы их не видит; на Vercel cookies передаются только по HTTPS.
- Роли лежат в таблице `user_roles`. Новый пользователь автоматически получает роль «клиент».
- Экран выбора роли показывается только после входа и только если ролей больше одной. Клиент с одной ролью сразу попадает в приложение.
- Выбранная роль хранится в httpOnly-cookie `pp_role`, но сама прав не даёт: сервер в каждом запросе сверяет её с базой. Подменённая cookie даёт отказ 403, и попытка пишется в журнал.
- Роль сотрудника действует 12 часов, потом её нужно выбрать снова.
- Три линии защиты:
  1. `proxy.js` — проверяет вход и роль до того, как откроется страница или API;
  2. сама страница или обработчик API проверяет ещё раз (`lib/server/session.js`);
  3. правила RLS в базе: пользователь видит только свой профиль и свои роли, админ — всё через функцию `has_role()`; писать роли может только сервер.
- Без входа — код 401 и страница «Нужно войти», без нужной роли — 403 и страница «Нет доступа».
- Ограничение попыток входа: после 10 неудачных попыток на одну почту или 30 с одного IP за 15 минут вход закрывается на 15 минут.
- Защита от подделки запросов с чужих сайтов: API принимает только JSON и проверяет заголовок Origin.
- Ошибки по-русски и без подсказок взломщику: на любую ошибку входа — «Неверная почта или пароль».

- Клиентские маршруты API (`/api/v1/projects`, `/cart`, `/orders`, `/interactions`, `/me/photos`) требуют **активную роль «клиент»**: модератор и администратор в роли «Администратор» получают 403 (это проверяют `test:api` и `test:auth`). Таблица прав — в разделе «Роли и тестовые учётные записи» выше и в [docs/architecture.md](docs/architecture.md).

## Двухфакторный вход для сотрудников

Модератор и администратор могут входить с кодом из приложения-аутентификатора (Google Authenticator, Яндекс Ключ, 1Password и другие). Это Supabase MFA, коды TOTP.

Включается флагом `REQUIRE_STAFF_MFA` в настройках Vercel или в `.env.local`:

- `REQUIRE_STAFF_MFA=true` — для ролей «модератор» и «администратор» код обязателен. При первом входе с такой ролью приложение показывает QR-код: его нужно отсканировать в приложении-аутентификаторе и ввести 6 цифр. Дальше при каждом входе с ролью сотрудника — только код. Сервер проверяет код в каждом запросе к админке (уровень сессии `aal2`), и в `proxy.js`, и в обработчике.
- Флаг не задан или `false` — код не спрашивается. **Так настроен демо-стенд**: иначе жюри не сможет войти в общие тестовые аккаунты, ведь код приходит только на один телефон. Подключённое раньше приложение-аутентификатор при выключенном флаге вход не блокирует.

Как проверить у себя: добавьте `REQUIRE_STAFF_MFA=true` в `.env.local`, запустите `npm run dev`, войдите как `admin@example.com` и выберите «Администратор». Автотест: `npm run test:mfa` (см. раздел «Запуск у себя»).

Убрать подключённый код у аккаунта: Supabase → Authentication → Users → пользователь → MFA factors → удалить.

## Журнал действий (ОТ-04)

- Таблица `audit_log`: когда (`at`), кто (`user_id`, `role`), что (`action`), над чем (`object_type`, `object_id`), чем закончилось (`result`: success / denied / error), подробности (`details`) и IP.
- Записываются: вход (успех и ошибка), регистрация, выбор роли, выход, отказ в доступе, изменение профиля, удаление аккаунта, подключение и проверка кода 2FA; проекты (`project.create/update/delete`), фото (`photo.upload_url/add/reorder/delete/view`), корзина (`cart.update/merge`), промокоды (`promo.validate`), заказы (`order.create/view/pay_test`), обращения (`interaction.create/message/view`), выгрузка и удаление данных (`account.export/delete_photos`). Попытки открыть чужой объект пишутся с результатом `denied`.
- Записи нельзя изменить или удалить никому, даже серверу с секретным ключом: это запрещают права и триггер в базе. Записи остаются и после удаления аккаунта.
- Экран `/admin/audit` (только администратор, D7 · SEC-15): фильтры — группа или действие, результат, пользователь (полный id или первые 8 знаков; в каждой строке ссылка «только этот пользователь»), даты «с / по» по Минску, тип и id объекта; «Показать ещё» — курсором без пропусков и повторов. Поиск по почте — отдельной формой: почта уходит только телом `POST`, в адрес и историю браузера не попадает. Форма фильтров работает без JS. Время — по Минску (UTC+3).

## База данных

Миграции лежат в `supabase/migrations/` и применяются командой `npm run db:migrate`. Применённые файлы записываются в служебную таблицу `private.schema_migrations`, поэтому повторный запуск ничего не ломает.

| Таблица | Что хранит |
|---|---|
| `profiles` | имя пользователя и дата создания; `id` совпадает с id в Supabase Auth |
| `user_roles` | роли пользователей; пара «пользователь — роль» уникальна |
| `audit_log` | журнал действий, только добавление |
| `products`, `product_sizes`, `product_options` | каталог: продукты, размеры (коэффициент цены), опции (обложка, ламинация, бумага, печать, поверхность) |
| `delivery_methods`, `promo_codes` | способы доставки и тестовые промокоды |
| `addresses` | сохранённые адреса получателя |
| `projects`, `project_photos` | проекты клиента (опции, статус, `version` — защита от затирания) и их фото в хранилище |
| `cart_items` | корзина на сервере |
| `orders`, `order_items`, `order_status_history` | заказы (номер `PP-ГГММДД-NNNNN`, суммы в копейках, ключ идемпотентности), состав-снимок, лента статусов |
| `interactions`, `interaction_messages` | обращения по заказу и переписка (клиент, бот, оператор) |
| `notifications`, `notification_settings`, `push_subscriptions` | уведомления и подписки на пуши |
| `analytics_events`, `moderation_reviews`, `data_requests` | обезличенная аналитика, модерация фото, запросы на удаление данных |

Пометки тестовых данных (S10, миграции 0004–0005): `orders.is_synthetic`, `analytics_events.is_synthetic`, `profiles.is_synthetic` (синтетические клиенты), `projects.is_demo` (демо-проекты жюри), `orders.is_demo` (заказ из приложения на демо-стенде, статусы двигает демо-тикер). Сводку для дашборда считает функция `analytics_summary(days, with_synthetic)` (только сервер).

Правила доступа (RLS) включены на всех таблицах: гость не видит ничего, клиент — только своё, модератор — очередь модерации, админ — всё; писать может только сервер после своих проверок. Фото лежат в приватном бакете `photos` (только JPEG/PNG до 25 МБ), путь `{user_id}/{project_id}/{uuid}.jpg`; загрузка и просмотр — только по подписанным ссылкам сервера (просмотр — 10 минут). Лимиты частоты — функция `rate_limit_hit` и таблица `private.rate_limits`.

Ещё в базе: тип `app_role` (client, moderator, admin), функция `has_role()` для правил доступа, триггер `on_auth_user_created` — новому пользователю создаёт профиль и даёт роль «клиент».

## Каталог и цены

- Каталог хранится в базе и приходит в приложение только через `GET /api/v1/catalog`: 5 продуктов (Lite, Classic, Premium, Печать фото, Цифровая печать), размеры, опции, цены, сроки, требования к фото, 5 способов доставки. Источник данных — `docs/superpicpac/superpicpac.md`.
- Требования к фото: JPEG или PNG до 25 МБ; на своём месте в печати ≥ 300 точек на дюйм — отлично, ≥ 150 — хорошо, 100–150 — предупреждение «может быть нечётко», < 100 — «будет размыто».

### Формулы (ОТ-07)

Деньги в базе — целые копейки и валюта `BYN`; даты — `timestamptz` (UTC), показываем по Минску (`Europe/Minsk`, UTC+3). Формулы одни и те же в интерфейсе и на сервере — `lib/pricing.js`, проверяются `npm run test:unit`.

| Что | Формула |
|---|---|
| Коэффициент размера книги | `k = 1 + 0,6 × (ширина × высота ÷ 400 − 1)`; 20×20 → 1, 21×30 → 1,345, 30×30 → 1,75. **Коэффициенты размеров тестовые — уточнить у Фотопринт** |
| Цена книги | `(база + надбавка_за_2_стр × (страниц − мин) ÷ 2) × k`, округление до 0,10. Проверка (20×20): Classic 60 стр. = 141,00; Lite 160 = 206,00; Premium 60 = 275,50 |
| Цена печати фото | `цена_отпечатка_размера × число_фото` |
| Надбавка опций | к цене книги (или отпечатка) прибавляется `price_delta_kop` выбранных опций; сейчас у всех опций 0 — на сайте опции цену не меняют |
| Строка заказа | `цена_за_единицу × количество` |
| Скидка промокода | `percent`: товары × % ÷ 100 (округление до копейки); `amount`: min(сумма кода, товары); `free_delivery`: 0. Код действует, только если товары ≥ мин. суммы и сейчас внутри срока действия |
| Доставка | 0, если промокод `FREESHIP` или (товары − скидка) ≥ «бесплатно от» способа; иначе цена способа |
| Итого | товары − скидка + доставка |
| Срок | сегодня по Минску + срок печати (книги 3 дня, фото 2) + дни доставки способа (от–до) |
| Номер заказа | `PP-ГГММДД-NNNNN`: дата по Минску + порядковый номер из последовательности базы (без случайных цифр и совпадений) |
| Точек на дюйм (книга) | `dpi = min(ширина_фото_px ÷ ширина_места_дюймы, высота_фото_px ÷ высота_места_дюймы)`, место = доля страницы × размер страницы в см ÷ 2,54 (`lib/layout.js`, `slotDpi`) |
| Точек на дюйм (печать фото) | длинная сторона снимка — на длинную сторону отпечатка: `dpi = min(длинная_px ÷ длинная_дюймы, короткая_px ÷ короткая_дюймы)` (`printDpi`) |
| Проверка dpi | ≥ 150 — без замечаний (≥ 300 — отлично); 100–149 — «может быть нечётко»; < 100 — «будет размыто» (`lib/checks.js`: `DPI_WARN = 150`, `DPI_BAD = 100`) |

## Каталог, карточка и редактор на устройстве (S02a–b)

- **Каталог без лишних запросов.** Главная и карточка продукта отрисовываются на сервере из той же базы, что `GET /api/v1/catalog` (главная обновляется раз в минуту, ISR). Браузер на этих страницах каталог не запрашивает; на остальных экранах — один общий запрос (`lib/useCatalog.js`).
- **Карточка продукта:** размер (у каждого — своя цена), обложка, ламинация страниц (по умолчанию как обложка), бумага, тип печати, поверхность, страницы, количество. Цена считается сразу по `lib/pricing.js` — той же формуле, что на сервере. Срок — по Минску: «Напечатаем за 3 дня — доставим ориентировочно 17–18 ноября» (печать + дни первого способа доставки), сроки и цены остальных способов — под спойлером. Блок «Требования к фото» с точными пикселями для выбранного размера.
- **Мои книги и фото:** несколько проектов на устройстве (IndexedDB) со статусами «Черновик», «В корзине», «Заказан». «Создать» для другого продукта открывает новый проект и не трогает прежние. Раздел «Заказанные»: «Открыть заказ» и «Заказать ещё раз» (копия проекта с теми же фото — заказанный проект не меняется).
- **Редактор:** шаги «Фото · Автомакет · Правки · Проверка · Заказ · Статус». Фото с устройства (JPEG/PNG, сразу несколько; на компьютере — перетаскиванием файлов в окно) или кнопкой «Тестовая галерея» (выбор фото из `public/demo-gallery`). По каждому фото видно «ждёт очереди / готовим… / не получилось» и кнопка «Повторить». Порядок: на телефоне — кнопки «раньше / позже», на компьютере — перетаскивание за значок ⠿ мышью или клавиатурой (Tab, пробел, стрелки, пробел; подсказки для экранного диктора на русском). «Правки»: кадрирование — «Заполнить место» или «Целиком» и что важнее оставить в кадре.
- **Проверка перед заказом:** пустые страницы, не поместившиеся фото, недостаточная резкость в печати (точек на дюйм на своём месте), неподдерживаемый формат (HEIC, WebP, GIF), файл больше 25 МБ. Каждое предупреждение объясняет проблему и что делать; кнопки «Заменить фото» и «Продолжить всё равно» (решение сохраняется в проекте, у вошедшего клиента — ещё и в журнале действий).
- Черновик сохраняется на устройстве сразу и переживает перезагрузку и закрытие браузера.

## Синхронизация, корзина и оформление (S02c)

- **Гость** работает только на устройстве: проекты и фото — в IndexedDB, корзина — в `localStorage`. Чтобы подтвердить заказ, нужно войти или зарегистрироваться; после входа приложение возвращает в корзину, а проекты и корзина гостя переносятся в аккаунт.
- **Вошедший клиент:** каждый проект синхронизируется с аккаунтом (`lib/sync.js`) через 1,2 с после изменения: `POST /api/v1/projects` → для каждого фото `upload-url` → `PUT` файла в хранилище → `POST photos` (сервер сам проверяет тип и размеры по байтам) → `PATCH photos/order` → `PATCH /projects/{id}` с `version`. Если проект изменили на другом устройстве (409), приложение перечитывает версию и сохраняет свои правки поверх. Без сети изменения ждут и уходят сами, когда связь вернётся. `serverId` и `version` хранятся в проекте на устройстве. Проекты аккаунта, которых нет на устройстве (вход с нового устройства), загружаются вместе с фото и порядком.
- **Корзина вошедшего** — на сервере (`/api/v1/cart`), её видно с другого устройства. Позиция, добавленная на устройстве, сначала ждёт загрузки фото («Переносим в аккаунт: загружено фото 5 из 12»), затем попадает в серверную корзину. Счётчик позиций — в шапке, с анимацией при добавлении.
- **Оформление:** получатель (имя, телефон `+375 (XX) XXX-XX-XX` с проверкой, почта), способ получения из каталога (5 способов) с зависимыми полями: пункт выдачи Европочты из тестового списка, отделение Белпочты по индексу, курьер — адрес и дата. «Сохранить адрес» — адрес появится кнопкой при следующем заказе (на устройстве). Промокод — видимое поле, «Применить» и «Убрать», сообщения «Промокод применён», «Не подходит: …», «Истёк: …» приходят с сервера. Расчёт «Товары → Скидка → Доставка → Итого» в BYN по `lib/pricing.js` сразу при любом изменении; итог заказа сервер считает заново. Оплата только тестовая: «Карта (тест)» или «ЕРИП (тест)», деньги не списываются.
- **Без дублей:** ключ `Idempotency-Key` создаётся на попытку оформления и хранится в IndexedDB до успеха. Двойное нажатие, повтор после обрыва связи или перезагрузки отправляют тот же ключ — сервер вернёт тот же заказ. Кнопка блокируется на время запроса, при ошибке сети — понятное сообщение и «Повторить», введённые данные не теряются.
- После успеха — номер заказа с сервера (`PP-ГГММДД-NNNNN`), ориентировочная дата доставки, проект переходит в «Заказанные».

## Заказы, поддержка, выход (S02d–e)

- **«Мои заказы»** — история из `GET /api/v1/orders`: номер, статус, позиции, сумма, дата; список обновляется раз в 15 секунд. Из списка открывается **экран заказа** (`GET /api/v1/orders/{id}`): состав (продукт, опции словами, число фото, миниатюры по подписанным ссылкам на 10 минут), «Товары → Скидка → Доставка → Итого» в BYN, тестовая оплата, получатель, способ и адрес доставки, ориентировочная дата.
- **Статусы — ровно 5 из ТЗ:** «Принят» → «Модерация» → «Производство» → «Готов / передан в доставку» → «Завершён». Лента показывает время каждого шага по Минску и причину смены. Мока ERP нет — демо-заказы двигает сервер при чтении: через 30 секунд после тестовой оплаты — «Модерация»; ещё через 30 секунд — «Производство» автоодобрением, если ни у одного фото нет флага модерации (с флагом заказ ждёт модератора, автоматика сама не отклоняет); дальше шаг каждые 30 секунд. Смена статуса — условным обновлением в базе, поэтому одновременные чтения не задваивают ленту (`lib/server/orderFlow.js`).
- **«Написать в поддержку»** на экране заказа: тема и сообщение → обращение привязано к заказу, бот сразу отвечает, к какому сроку ответит оператор (24 часа). Обращения и переписка видны в заказе и в админке → «Заказы» (последние заказы и обращения из базы, без ФИО и адресов). Чат оператора и смена статуса с причиной — не сделаны.
- **Выход (M-01):** кнопка «Выйти» сначала отправляет в аккаунт всё, что ещё не ушло (`syncAll()`). Если не получилось (нет связи) — предупреждение «Не все изменения сохранились в аккаунте» с выбором «Повторить» или «Выйти без них». Затем с устройства стираются черновики и фото (IndexedDB «picpac»: проекты, фото, ключ заказа, очередь удалений), гостевая корзина, форма оформления и адреса (`localStorage` `picpac:*`), кэш «кто вошёл», пуш-подписка — и только потом сервер закрывает сессию (`lib/device.js`). При удалении аккаунта устройство тоже очищается. После входа проекты (с фото и порядком), корзина и заказы загружаются из аккаунта.
- **Черновик на устройстве** записывается в IndexedDB не позже чем через 0,15 с после изменения (и сразу при уходе со страницы), даже при быстром добавлении многих фото подряд.
- **Экран входа** — без паролей: «Данные для входа жюри — в README проекта», кнопка «Продолжить как гость». **Профиль гостя:** «Профиль», объяснение, «Войти», «Зарегистрироваться», «Назад к каталогу».

## ИИ-редактор фото: анализ, автоулучшение, команды (S03a–b)

Шаг «Правки» в редакторе. Всё работает на устройстве, без сети и бесплатно; тяжёлый код грузится только при открытии редактора.

- **Анализ каждого фото** при добавлении — в Web Worker (`lib/photo/analyze.worker.js`, OffscreenCanvas, снимок уменьшается до 512 точек), интерфейс не замирает. Метрики (`lib/photo/analyze.js`): средняя яркость и процентили, доля пересвеченных и провалившихся в тень точек, контраст, цветовой оттенок по «серому миру» и по светлым участкам, резкость (дисперсия лапласиана, делённая на дисперсию яркости), шум (метод Иммеркера), печатный dpi на своём месте (как в «Проверке»). Итог — список проблем и оценка 0–100. **Значки на миниатюрах:** «Темно», «Пересвет», «Размыто», «Мало точек для печати» (и «Оттенок»), «Улучшено», «ИИ». Пороги подобраны на «Тестовой галерее»: 8 хороших фото без значков, тёмные, пересвеченное, жёлтое, размытое и маленькое — со своими значками (unit-тест).
- **Автоулучшение** — только для явно плохих фото (тёмное, пересвет, оттенок, блёклое), мягко: экспозиция с «плечом», светлые и тени, баланс белого, контраст, лёгкая насыщенность. Хорошие фото не трогаем. Отмена на одном фото («Отменить улучшение» / «Вернуть улучшение»), «Отменить все улучшения», выключатель **«Улучшать автоматически»** (по умолчанию включён) — в редакторе и в профиле (хранится на устройстве, `picpac:autoEnhance`). Подсказка честно говорит о пределах: полностью белое не восстановить, сильную размытость не исправить, при печати предупредим.
- **Правки неразрушающие (МП-03):** оригинал фото не меняется; в проекте хранится только `photo.edits` = `{ auto, autoOff, manual, ops }` (формат — в `lib/photo/edits.js` и `lib/photo/adjust.js`). Правки переживают перезагрузку (IndexedDB) и синхронизацию: у вошедшего клиента они уходят в аккаунт в `options.settings.edits` по id фото на сервере и возвращаются на новое устройство. «Вернуть оригинал» работает всегда.
- **Ручная настройка:** Яркость, Контраст, Тепло, Насыщенность, Светлые, Тени (от −100 до +100). Превью — canvas 2D: уменьшенный до 1280 точек оригинал правится таблицами по 256 значений на канал (10–20 мс на кадр), та же функция `applyEdits` пойдёт в печатную версию.
- **«Что изменить?»** — поле и подсказки «Ярче», «Теплее», «Убрать пересвет», «Размыть фон», «Убрать солнце». Разбор словарём на устройстве (`lib/photo/commands.js`): синонимы и формы слов («ярче», «посветлее», «осветли», «затемни», «контрастнее», «похолоднее», «убери желтизну», «насыщеннее», «осветли тени», «чёрно-белое»…), усилители «чуть», «немного», «сильнее», «намного», «максимально», отрицания («не так ярко», «не такое тёмное», «слишком ярко»), несколько правок сразу («намного ярче, холоднее»), «ещё» повторяет последний шаг, «улучши», «отмени», «верни оригинал». Свет и цвет применяются мгновенно; на всё есть ответ словами, непонятное — «Не понял «…». Попробуйте: …». «Убрать солнце» работает (см. следующий раздел); «Размыть фон», «осветли / затемни выделенное», «убери выделенное» и «убери X» работают через выделение касанием (D1, раздел ниже).
- **Управление:** «До / после» — ползунок (слева оригинал, справа правка) и удержание кнопки «Удерживайте — оригинал» или самого фото; «Применить» (сохраняет и переходит к следующему фото), «Отменить» (история шагов), «Вернуть оригинал». Здесь же — кадрирование («Заполнить место» / «Целиком», что важнее в кадре).
- **Размер JS** (`.next/diagnostics/route-bundle-stats.json`, `firstLoadUncompressedJsBytes`): главная 500 307 → 501 304 Б (+997 Б — данные правок для синхронизации), карточка продукта 505 655 → 506 652 Б, редактор 572 878 → 584 467 Б. Сам ИИ-редактор (`components/editor/PhotoEditor.js`) и воркер анализа — отдельные куски, грузятся только на шаге «Правки» и при добавлении фото.

## ИИ-редактор: «убери солнце», печатная версия, понятные команды (S03c–e, часть)

- **Команды «наоборот» и разговорные формы** (по отчёту критика): «поменьше яркости», «яркость пониже», «контраст пониже», «поменьше насыщенности», «чуть поменьше тепла», «сделай менее ярким», «менее контрастно», «слишком контрастно», «слишком жёлтое», «слишком синее», «не надо желтизны», «желтовато», «темновато», «пересвечено», «засвечено», «приглуши свет», «больше света», числа «яркость +30», «контраст минус 10»; вежливые слова («пожалуйста», «давай», «ну») не мешают. После «сильнее» и «ещё» ответ — «Сделали ещё ярче» (без «ещё ещё»). Все фразы критика — в `tests/unit/photo-commands.test.mjs`.
- **«Убери солнце», «убери блики»** (`lib/photo/local.js`, без нейросетей и сети): поиск самой яркой небольшой круглой области (большое светлое небо — это пересвет, не солнце; точка меньше 0,8 % кадра — фонарь или отблеск, не солнце, а для «убери блики» подходит) → круг вместе с ореолом → заливка «push-pull» по пирамиде из цветов вокруг круга: ядро заменяется целиком, ореол гаснет плавно к краю круга. Правка хранится в `photo.edits.ops` маленьким объектом `{ kind: "heal", cx, cy, r }` (доли кадра, без файла маски), применяется в превью и в печатной версии в полном разрешении; вне круга пиксели не меняются. Повтор — «Солнце уже убрано», «Отменить» возвращает. Нет яркого пятна — честный ответ. Пределы: на месте большого солнца остаётся мягкое пятно ровного цвета; на ночной улице «солнцем» окажется самый яркий фонарь.
- **Печатная версия (S03e):** при «Подтвердить заказ» каждое изменённое фото собирается на устройстве в полном разрешении со всеми правками (`lib/photo/print.js` → воркер `lib/photo/print.worker.js`, OffscreenCanvas, полосами по 256 строк) и загружается рядом с оригиналом: `POST /api/v1/projects/{id}/photos/{photoId}/print` (ссылка) → `PUT` файла → `PUT …/print { path, edits }`. Сервер проверяет файл (JPEG, тот же размер кадра, свой путь) и записывает `project_photos.print_path` и правки; снимок заказа `order_items.snapshot.photos[].edits.print` содержит путь, размеры и байты печатной версии, `photos[].path` — оригинал. На кнопке — «Готовим фото к печати: 1 из 2». Неизменённые фото печатаются с оригинала; если правки сняли — `PUT { path: null }`; если файл не собрался на устройстве — правки записываются параметрами, заказ не останавливается. Печатная версия удаляется вместе с фото, проектом, «Удалить мои фото» и аккаунтом. Если правки не удалось сохранить ни файлом, ни параметрами (нет связи) — заказ не оформляется, кнопка «Повторить».
- **Значки на миниатюрах** в «Правках» на телефоне не обрезаются: внизу миниатюры, полным словом.

## ИИ-редактор: выделение касанием, ластик, резкость для печати (D1, S03c)

Всё на устройстве, без отправки фото в интернет. Модели лежат на нашем сайте (`public/models`, `public/ort`, лицензии — `public/models/README.md`), грузятся только по нажатию и кэшируются сервис-воркером; со строгой CSP (`'wasm-unsafe-eval'`, воркеры только свои).

- **«Выделить касанием»** (шаг «Правки»): SlimSAM (`slimsam-77-uniform-boxes`, int8, 13,6 МБ, Apache-2.0) через `@huggingface/transformers` в воркере `lib/photo/ai.worker.js`. Тяжёлая часть — один раз на фото (10–20 с на компьютере, прогресс и «Отмена» — она останавливает воркер и освобождает память), лёгкая — на каждое касание (≈ 0,3 с). Касание — «это предмет», режим «− Убрать часть» — «это не он», «Отменить точку», «Сбросить». Выделение подсвечивается на фото. Проверка устройства: нужен WebAssembly SIMD и не меньше 4 ГБ памяти (`navigator.deviceMemory`), иначе — честный ответ, команды и ползунки работают.
- **Действия с выделенным:** «Размыть фон» (всё вне выделения, предмет не «растекается» ореолом), «Осветлить», «Затемнить», «Убрать» — ластик MI-GAN (`migan_pipeline_v2.onnx`, 28 МБ, MIT): вырезка вокруг предмета с полями, маска расширяется (край и тень уходят), результат вклеивается только внутри маски с мягким краем.
- **Командой:** «размой фон», «осветли выделенное», «затемни предмет», «убери выделенное». «Убери машину / человека / X»: если предмет уже выделен — убираем выделенное; если нет — «Сам найти «машину» пока не умею. Коснитесь того, что убрать…» и сразу включается выделение (поиск предмета по слову в облаке — этап D6).
- **Как хранится:** правка `{ kind: "mask", act, id, mask: { w, h, rle } }` в `photo.edits.ops` — маска ≤ 320 точек, сжатая RLE (обычно 0,3–1 КБ), до 8 правок по выделению на фото, общий размер правок проекта ≤ 45 КБ (сервер принимает 50 КБ). Правки неразрушающие, «Отменить» и «Вернуть оригинал» работают, переживают перезагрузку и синхронизацию с аккаунтом.
- **Превью = печать:** одни и те же чистые функции (`lib/photo/mask.js`) в превью и в воркере печатной версии; маска растягивается на любой размер кадра с мягким краем. Порядок: ластик → свет и цвет → местные правки по порядку. Ластик в печатной версии считается заново в **полном разрешении** (вырезка ≤ 1024 для нейросети, вклейка в полный кадр) — e2e `editor-mask.spec.mjs` скачивает печатную версию заказа и проверяет: размер как у оригинала, фон размыт, мяча нет, собака не изменилась.
- **«Резкость для печати ×2»** — для фото со значком «Мало точек для печати» и длинной стороной ≤ 1500: UpscalerJS `esrgan-slim` ×2 (0,9 МБ, MIT) в воркере на WebGL (без WebGL — честный отказ: на процессоре это минуты). Прогресс и «Отмена». Увеличенный файл хранится на устройстве (IndexedDB), в правках — только `upscale: 2`; «Проверка» считает dpi ×2; печатная версия — ровно ×2 по сторонам (сервер принимает такой размер только с этой правкой). На другом устройстве ×2 считается заново при заказе.
- **Обход ошибки старых Chrome:** Turbopack запускает все воркеры через один файл с параметрами во фрагменте адреса (`#params=`); Chrome 111 брал из кэша адрес первого воркера, и второй воркер (ИИ, печать) молча выполнял код анализа фото. `lib/workerShim.js` переносит параметры в `?params=` — у каждого воркера свой адрес.
- **Размер JS главной не вырос:** `firstLoadUncompressedJsBytes` до (тег `night-final`) и после: главная 511 827 → 511 881 Б (+54 Б — версия сборки), карточка 517 322 → 517 376 Б, редактор 598 007 → 598 142 Б. transformers, onnxruntime и tfjs — только в воркерах; двух копий ORT и лишних `.wasm` в сборке нет (`turbopack.resolveAlias`).
- **Пределы:** первое выделение на телефоне может занять 20–60 с и до ~2 ГБ памяти (на компьютере 10–20 с); ластик на сложной текстуре оставляет мягкое пятно; WebGPU пока не используется (только WebAssembly).

## Безопасность

Все меры по пунктам SEC-01…SEC-24, как они проверены и **открытые замечания** независимой проверки (предел 100 Мп, лимиты не на всех изменяющих маршрутах, маскирование данных для модератора, фильтры журнала) — в [`docs/security.md`](docs/security.md). Коротко:

- **Строгая CSP с nonce** (`proxy.js` → `lib/server/csp.js`): у каждой страницы свой nonce, скрипты без него не выполняются; `frame-ancestors 'none'`, `object-src 'none'`. Поэтому страницы рендерятся на каждый запрос (вместо ISR каталог кэшируется в памяти сервера на 60 с). Плюс HSTS, `Permissions-Policy` (камера, микрофон, геолокация выключены), `Cross-Origin-Opener-Policy`, `nosniff`, `X-Frame-Options: DENY`, без `X-Powered-By`.
- **Единый формат ошибки** везде, включая отказы `proxy.js`: `{ ok:false, error:{ code, message, requestId } }`; неизвестный адрес `/api/…` → JSON 404, неверный метод → JSON 405 с заголовком `Allow` (список маршрутов — `lib/apiRoutes.js`, создаётся `node scripts/gen-api-routes.mjs`, unit-тест следит за актуальностью).
- **Лишние поля в запросах отклоняются** (400): все схемы `zod` строгие.
- **Удаление проекта или фото во время оформления заказа** не ломает заказ: строка удаляется только у незаказанного проекта, файлы — после.
- **Журнал**: чтение чужого проекта и перенос чужого проекта в корзину — отказ (`denied`); отказы гостю пишутся не чаще 10 раз в минуту с одного IP.
- **Удаление аккаунта** (SEC-17): удаляются фото и печатные версии в хранилище, проекты, корзина, адреса, подписки; заказы обезличиваются (получатель и адрес стираются) и остаются для отчётности. Почта остаётся в неизменяемом журнале действий — он нужен для разбора инцидентов.
- **Сессия** (D7 · SEC-22): роли выдаёт функция базы `session_roles()` только живой сессии — `session_id` из токена должен быть в `auth.sessions`. После выхода, «выйти везде» или удаления аккаунта старые куки сразу не дают доступа (API — 401, `/api/v1/me` — гость, админка — 401), хотя подпись токена ещё верна.
- **Лицензии** (SEC-24): `npm run licenses:check` (входит в `test:all`) — код выхода 1, если у рабочей зависимости GPL/AGPL или лицензия не указана; таблицы и модели — [`docs/licenses.md`](docs/licenses.md).
- **Поиск секретов**: `npm run security:scan` — файлы репозитория, вся история git, собранный фронтенд и сводка `npm audit`.
- **Сбой «кто вошёл»** (`GET /api/v1/me`) больше не делает из клиента гостя: «гость» — только по ответу сервера, при сбое — повтор с отсрочкой; корзина и синхронизация переключаются на аккаунт сами, в корзине — «Повторить».

## Установка как приложение (S07)

PicPac — PWA: устанавливается значком и работает без сети. Подробно по платформам — [docs/platforms.md](docs/platforms.md).

- **Android и компьютер (Chrome, Edge):** «Профиль» → «Установить приложение» или значок установки в адресной строке.
- **iPhone (Safari):** «Поделиться» → «На экран „Домой“» → «Добавить». Пуши на iPhone работают только так, с iOS 16.4.
- **Без сети:** открываются главная, «Мои книги», редактор с черновиками и корзина. Остальные страницы показывают «Нет сети — черновики сохранены на устройстве». Фото вошедшего клиента ждут сети и загружаются сами («Фото загрузятся, когда появится связь: N»).
- **Как устроено:** манифест — `app/manifest.js`; иконки — `public/icons/`, `app/icon.svg`, `app/apple-icon.png`, `app/favicon.ico` (генератор `node scripts/make-icons.mjs <папка>` из `public/logo.svg`); сервис-воркер — `public/sw.js`, регистрация и тост «Есть новая версия — Обновить» — `components/Pwa.js`.
- **Кэш:** статика и оболочка — сначала кэш; страницы — сначала сеть (через 4 с — сохранённая копия); каталог — из кэша с обновлением в фоне. API с данными пользователя не кэшируется. Версия кэша — коммит сборки, старые кэши удаляются.
- **Прямые ссылки:** `/orders/{id}`, `/cart`, `/product/{slug}`, `/editor?project={id}`. Гость попадает на вход и возвращается обратно.
- **Проверка:** `npx playwright test e2e/pwa.spec.mjs` (входит в `npm run e2e`).

## Статистика и демо-данные (S10)

**Дашборд:** «Админка» → «Статистика» (`/admin/stats`, только роль «Администратор»; API — `GET /api/v1/admin/stats?days=7|30&source=all|real`). Фильтр 7/30 дней, переключатель «Все данные / Только реальные», подпись «демо-данные» или «реальные». У каждой метрики — «?» с формулой.

**События** пишет само приложение в свою базу (`POST /api/v1/events`, без сторонних счётчиков): просмотр продукта, создание проекта, загрузка фото, время на шагах редактора (только пока вкладка видна), ИИ-правка (автоулучшение, команда), добавление в корзину, начало оформления. Заказ создан и тестовая оплата пишет сервер. Без персональных данных: сеанс — случайный id, новый каждый день; пользователь — только хеш SHA-256 с солью `ANALYTICS_SALT`. Лимит — 30 пачек в минуту на сеанс.

### Формулы статистики (ОТ-07)

| Метрика | Формула |
|---|---|
| Участник | хеш пользователя после входа, иначе id сеанса гостя (новый каждый день) |
| Шаг воронки | число разных участников с событием шага за период |
| Конверсия шага | шаг ÷ предыдущий шаг × 100% |
| **Из добавивших в корзину оплатили** | участники с тестовой оплатой ÷ участники с добавлением в корзину × 100% |
| Медиана времени на шаге | середина отсортированных замеров (при чётном числе — среднее двух средних); время считается, только пока вкладка видна |
| Где бросают | участники без добавления в корзину, по последнему шагу редактора; доля от всех таких |
| Проекты с ИИ-правками | участники с «ИИ-правкой» и «создан проект» ÷ участники с «создан проект» × 100% |
| Автоулучшенные фото | сумма фото, к которым применилось автоулучшение |
| Заказы сегодня | созданы с 00:00 по Минску |
| В работе | статусы «Принят», «Модерация», «Производство» сейчас |
| Просрочено | не «Готов / передан в доставку» и не «Завершён», крайний срок готовности (`eta_to`) прошёл |
| На модерации | статус «Модерация» сейчас |
| Обращения без ответа | статус «Ждёт ответа»; отдельно — у кого срок ответа (`sla_due`) прошёл |
| Выручка (тест) | сумма «Итого» заказов с тестовой оплатой за период (по `paid_at`), деньги не списывались |

Проценты и медианы считает `lib/analyticsCore.js` (проверяет `tests/unit/analytics.test.mjs`), агрегаты — функция базы `analytics_summary`.

### Повторная загрузка демо-данных (без секретов)

Нужен только файл `.env.local` (`vercel env pull .env.local`); пароли и ключи в командах не нужны.

| Команда | Что делает |
|---|---|
| `npm run seed` | создаёт демо-аккаунты жюри (один раз; пароль — из `SEED_PASSWORD`, не меняется) |
| `npm run seed:catalog` | каталог, размеры, доставка, промокоды |
| `npm run seed:demo` | синтетический набор + «живые» демо-аккаунты: у `client@example.com` 2 проекта (книга Lite на 12 фото из тестовой галереи, среди них «плохие»; печать фото), 5 заказов во всех статусах, обращение с ответом оператора |
| `npm run seed:synthetic` | только синтетический набор |
| `npm run reset:demo` | вернуть демо в исходное состояние: удалить строки `is_demo`/`is_synthetic`, синтетических, `e2e-…` и `critic-…@example.com` пользователей с их файлами, затем снова `seed:demo`. Тестовых пользователей моложе 30 минут не трогает (тест или проверка может ещё идти; `-- --all` — удалить и их). `-- --clean` — только удалить, `-- --dry-run` — только посчитать. Журнал действий не трогается |

Повторный запуск любой команды безопасен: старые синтетические и демо-строки сначала удаляются, дублей нет.

**Синтетический набор (ТЗ, раздел 8), детерминированный (seed 20261112):** 200 клиентов `synthetic-001…200@example.com` (имена собраны из списков, телефоны `+375 (00) …` — несуществующий код, случайный пароль нигде не хранится, войти нельзя), 523 заказа за 60 дней во всех 5 статусах (старые — завершены, свежие — в работе, ~2% просрочены), 320 обращений с темами (где заказ, адрес, сроки, промокод, чек, брак/перепечатка) и SLA 24 ч (перепечатка — 48 ч), ~14 900 событий воронки (у каждого заказа — полная цепочка, плюс сеансы, остановившиеся раньше). Допущения: доля оплативших из корзины ~60–75%, медианы шагов 50–160 с, суммы — по ценам каталога. Демо-заказы клиента помечены `is_synthetic`, поэтому демо-тикер их не двигает и жюри видит все 5 статусов; новые заказы жюри двигаются как раньше.

## Известные ограничения

Честно, на момент тега `night-s12-fix1` (исправления замечаний проверяющих на финальном этапе). Подробности — в [docs/test-report.md](docs/test-report.md).

**Не сделано:**

- **Мок ERP и ручная смена статуса.** Статусы демо-заказов двигает таймер при чтении заказа (шаг 30 с); приём событий производства `POST /api/v1/erp/events` и смена статуса администратором с обязательной причиной — не сделаны.
- **Модерация.** Очереди модератора и проверки фото на неприличное (nsfwjs) нет: на демо все заказы проходят «Модерацию» автоодобрением. Маскирования телефона и почты для модератора нет (SEC-14).
- **Поддержка:** бот отвечает на обращение сразу; очереди и чата оператора нет (ответ оператора есть только в демо-данных).
- **Пуши и напоминание о забытой корзине** не сделаны; центр уведомлений в профиле — список сообщений приложения на этом устройстве.
- **ИИ:** нет облачных правок Cloudflare и поиска предмета по слову («убери машину» просит коснуться предмета). Выделение касанием, ластик, «Размыть фон» и резкость для печати — на устройстве (D1).
- **Доступность:** автоматическая проверка axe (`npm run test:a11y`, 7 ключевых страниц на телефоне 390×844, светлая и тёмная тема) — 0 серьёзных и критических нарушений; ручного прохода с экранным диктором (VoiceOver, TalkBack) не было; режима «Крупный текст» нет.
- **Админка:** нет фильтров журнала, правки каталога и цен, управления пользователями.
- **Сохранённые адреса** хранятся на устройстве (таблица `addresses` в базе есть, API нет). Сброса пароля нет.

**Известные дефекты** (найдены проверяющими):

- «Убери солнце» — без нейросети: ищет почти белое ровное ядро с ореолом в верхней части кадра. На фото галереи находит солнце только на трёх снимках с солнцем, на остальных честно отвечает «Не нашёл солнце на этом фото — ничего не меняю». На реальных фото с солнцем за дымкой может не найти.
- Анализ фото в редакторе без сети не работает (модели и воркер грузятся из сети при первом открытии).
- Скорость: JS первой загрузки главной — 154 КБ при бюджете 150; в условиях Lighthouse LCP главной 2,18–2,28 с — выше бюджета 2,0 с ([docs/platforms.md](docs/platforms.md)).
- После выхода перехваченный токен доступа действует до своего срока (≤ 1 ч).

**Условности прототипа:**

- Оплата только тестовая («Карта (тест)», «ЕРИП (тест)»), деньги не списываются.
- Коэффициенты цен размеров, кроме 20×20, и цены цифровой печати, кроме 10×15, — **тестовые, уточнить у Фотопринт**.
- Все пользователи, заказы и обращения синтетические; реальные iPhone и Android не проверялись (только Chrome на компьютере в режиме телефона).
